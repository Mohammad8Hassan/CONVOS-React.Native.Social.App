# CONVOS (RN-Social-App)

React Native / Expo social app: conversations, friends, invites, push notifications, ads. Backend is Firebase (Auth, Firestore, Storage). Android is the primary target (iOS has never been configured for ads).

- Package name / bundle id: `com.mohammadHassan.CONVOS`, Expo slug `CONVOS`
- Entry: `node_modules/expo/AppEntry.js` -> [App.js](App.js) -> [Navigation.js](Navigation.js)
- State: Redux Toolkit ([store.js](store.js), [features/](features/), theme only); screens in [screens/](screens/), shared helpers/components in [shared/](shared/)
- Lint: `yarn lint` (ESLint 9 flat config in [eslint.config.js](eslint.config.js): `no-undef`, react-hooks rules). Run it after edits.

## Code layout (after the refactor)

Screens only wire things together; logic and UI pieces live next to them:

| Folder | Contents |

Conventions worth keeping:
- Read another user's doc with `getUserProfile(db, uid)`, never `getDoc(...).data().Photo`. On a cold start the emulator network is not up yet and Firestore answers from an empty cache (`data()` undefined) or throws "client is offline".
- Refactored files carry `REFACTOR NOTE:` comments saying how the code used to be. Remove them once nobody needs the history.
- `screens/Home.js`, `EditProfile.js`, `Invites.js` and `Settings.js` have **not** been split yet (see TODO).
- Package manager: **yarn 1.x** (`yarn.lock` is the lockfile). Do not create `package-lock.json`.

## Backend (Firebase project `convos-app-1`)

- [firestore.rules](firestore.rules), [firebase.json](firebase.json), [.firebaserc](.firebaserc), [functions/](functions/) (Cloud Functions, Node 22, region `europe-west1`, set by `REGION` in [functions/index.js](functions/index.js); must match the Firestore location and the region passed to `getFunctions` in the app). Deploy with `npx firebase-tools deploy --only firestore:rules` / `--only functions`. The user deploys; do not deploy without being asked.
- **Conversation passwords** (in progress, phased so published app versions keep working):
  - Phase 1 (backend, additive): callables `setConversationPassword` and `joinConversation`, hashed secrets in `ConversationSecrets/{id}` and attempt counters in `JoinAttempts/*` (both closed to clients by rules), [functions/scripts/migrate-passwords.js](functions/scripts/migrate-passwords.js). The plaintext `password` field on `Conversations/{id}` is **still there** and the old app still reads it.
  - Phase 2 (app, **done in code, needs the new build + a functions redeploy**): [services/conversations.js](services/conversations.js) calls the functions (`getFunctions(getApp(), 'europe-west1')`). `createConversation` no longer writes `password` (it calls `setConversationPassword`, and deletes the conversation if that fails); Home joins through `joinConversation`; the Invites screen joins through `joinConversation` too (a valid invite replaces the password); the participants modal no longer shows the password; the form has no default password. Members cannot see the password any more (decision: hash only, no encryption).
  - Phase 3 (rules, **written and tested in the emulator, not deployed yet**): [firestore.rules](firestore.rules) is now per-collection and strict (users readable one at a time, not listable; conversations / participants / comments only for the author and participants; no client self-join: only `joinConversation` adds participants; invites can only be created by the conversation author, so they can't be forged to skip a password; narrow cross-user writes for friend requests and unread counters). `firestore.rules.phase1` is the rollback copy. Deploying it **breaks app versions that still do the old direct writes/reads**, so deploy it only after the new app build is the one users have (or accept that). The old demo conversations still have a plaintext `password` field: with the new rules only members can read it; remove it later with `node scripts/migrate-passwords.js --apply --scrub` (in `functions/`).
  - Invites: only the conversation author invites (only `createConversation` writes invite documents; the "Invite Participant" menu item in Details has always been commented out). Rules and `joinConversation` both enforce it. If participants are ever allowed to invite, change both.
  - Rules test suite: `scratchpad/rules-test` was a throwaway harness (87 checks, `@firebase/rules-unit-testing` + Firestore emulator via `npx firebase-tools@13.35.1 emulators:exec`, needs Java 17; firebase-tools 14+ needs Java 21). Recreate it if the rules change; the scenarios are the app's real flows (friend request/approve/remove, join, leave, comments, unread, invites, delete conversation).
- Remaining backend risks: every signed-in user can read any user's document (email, `ExpoPushToken`) because push notifications are sent from the phones; moving push sending into Cloud Functions would remove that. `storage.rules` is a draft (profile photos only). Consider Firebase App Check.

## How to run

The app **cannot run in Expo Go** (native modules: `react-native-google-mobile-ads`, `expo-dev-client`, etc.). It needs a development build.

1. First time / after any native dependency or `app.json` plugin change, build and install the dev client (PowerShell/bash with JDK 17 on PATH):
   `npx expo run:android` (takes ~8 min cold; generates `android/`).
2. Day to day, only Metro is needed: `npx expo start --dev-client`, then open the app on the emulator.
3. Emulator + Metro: run `adb reverse tcp:8081 tcp:8081`. If the dev launcher shows a blank screen, open the app via
   `adb shell am start -a android.intent.action.VIEW -d "exp+convos://expo-development-client/?url=http%3A%2F%2F10.0.2.2%3A8081"`.
4. If `adb devices` shows `offline`: `adb kill-server && adb start-server`.
5. `INSTALL_FAILED_UPDATE_INCOMPATIBLE` on install means an old build signed with a different key is installed: `adb uninstall com.mohammadHassan.CONVOS`, then reinstall.

`npx expo-doctor` currently passes 21/21. A quick bundle check: `npx expo export --platform android --output-dir <tmp>`.

### Code / config changes made

- [App.js](App.js)
  - Firebase auth persistence: `initializeAuth` and `getReactNativePersistence` now come from `'firebase/auth'` (the `firebase/auth/react-native` path no longer exists).
  - Removed `expo-navigation-bar` `setBackgroundColorAsync` call and the unused `Platform` import (the API is gone under edge-to-edge).
  - Wrapped the app in `<GestureHandlerRootView style={{flex:1}}>` (required by gesture-handler 2.32; otherwise Login crashes with "must be used as a descendant of GestureHandlerRootView").
- [app.json](app.json)
  - `splash` moved into the `expo-splash-screen` config plugin (top-level `splash` is no longer valid).
  - Added the `react-native-google-mobile-ads` plugin with `androidAppId`.
  - **Kept** the top-level `"react-native-google-mobile-ads": { "android_app_id": ... }` key. The library's Gradle script (`app-json.gradle`) reads it from the root of app.json, and the build fails with `Cannot get property 'googleMobileAdsJson'` without it. Expo warns that this is an unknown root key; that warning is expected.
  - Removed `androidStatusBar` and `updates.fallbackToCacheTimeout` (obsolete).
- [babel.config.js](babel.config.js): removed the manual `react-native-reanimated/plugin` (`babel-preset-expo` configures worklets itself).
- `expo-file-system` -> `expo-file-system/legacy` in Details, EditProfile, Friends, Home, Invites, NewConv, Settings (the code uses the old `getInfoAsync` / `createDownloadResumable` / `cacheDirectory` API, which moved to `/legacy` in recent SDKs).
- [screens/EditProfile.js](screens/EditProfile.js): `ImagePicker.MediaTypeOptions.Images` -> `['images']`.
- [screens/Home.js](screens/Home.js), [screens/Details.js](screens/Details.js): notification handlers use `shouldShowBanner` + `shouldShowList` instead of the deprecated `shouldShowAlert`.
- [screens/Settings.js](screens/Settings.js): `NavigationBar.setBackgroundColorAsync/setButtonStyleAsync` replaced with `NavigationBar.setStyle('dark' | 'light')`.
- [screens/Login.js](screens/Login.js), [shared/SystemMessage.js](shared/SystemMessage.js): added the missing `Platform` import (it was used but never imported; older RN tolerated it).
- Edge-to-edge fix: `SafeAreaView` is now imported from `react-native-safe-area-context` (instead of `react-native`) in Details, EditProfile, ErrorScreen, Friends, Home, Invites, Network, NewConv, Settings, Verify. RN's built-in `SafeAreaView` does nothing on Android, and Android 15+/SDK 57 draws edge-to-edge, so content overlapped the status and navigation bars.
- [screens/Home.js](screens/Home.js): guards for missing Firestore user docs (`snapShot.exists()` / `info.exists()`) that log `"Users doc missing for ..."` instead of throwing `Cannot read property 'Photo' of undefined`.
- `.gitignore`: added `/android` and `/ios`.

5. Gradle: `Cannot get property 'googleMobileAdsJson'` -> restored the root key in app.json.
6. adb install: `INSTALL_FAILED_UPDATE_INCOMPATIBLE` (old SDK 45 dev build, different signature) -> uninstalled the old app from the emulator.
7. Runtime: `Property 'Platform' doesn't exist` in Login -> added imports.

10. Layout overflowing system bars on screens such as "invite participant" -> SafeAreaView change above. The Home screen was verified visually; the invite-participant screen was **not** re-checked after the fix.

Still open:

- **Friends**: the search uses the whitespace-stripped ID but Send/Block use the ID as typed (a trailing space breaks Send); blocking a friend shows two toasts ("Removed" then "Blocked"); friend-request docs store `Email: res.data().email` (lower-case field, probably a typo for `Email`); if "Approve" finds the request gone, the modal spinner stays on.
- Duplicate `alignItems` keys in styles: [screens/Conversations.js:174](screens/Conversations.js#L174), [screens/Home.js:649](screens/Home.js#L649) (ESLint `no-dupe-keys`).
- Details: `Notifications.setNotificationHandler` is set on every render and is global, so Home can overwrite it while a conversation is open.
- Firebase web config (including API key) is hard-coded in [App.js](App.js). Firebase web API keys are not secrets, but make sure Firestore/Storage rules and API key restrictions are tight.
- Avatars appeared as empty circles in the emulator before the cold-start guards; re-check, they may be fixed.
